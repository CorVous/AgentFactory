# Groups are an author-only convenience; the bus stays name-addressed

A topology may declare named **Groups** and reference them via `@<name>` in routing fields (`supervisor:`, `submitTo:`), peer fields (`acceptedFrom:`, `peers:`), and the launcher entry (`entry:`). All `@group` references resolve to one or more concrete **Instance Names** at launch time before any peer spawns; the bus protocol, the **Habitat**, and every rail continue to see only concrete names. Groups exist so anonymous peers can participate in routing without the topology having to invent a name to reference them by — they are not a runtime addressing primitive.

## Why

- **Anonymity is the actual goal.** A topology like `authority-mesh.yaml` already auto-names worker peers (`<breed>-<shortName>` slugs). Today `supervisor:` requires a concrete name on the receiving end, so the *target* of a worker's escalation has to be named even when the worker itself doesn't. `@group` references close that gap: workers can declare `supervisor: @authority` against a single-member group whose only member is anonymous, with no name appearing anywhere in the YAML.
- **The bus never needs to learn about groups.** Resolving `@group` to concrete names at launch keeps `${BUS_ROOT}/${name}.sock` unchanged, keeps `agent_send({to})` unicast, and keeps `Habitat.supervisor` / `Habitat.submitTo` as scalar strings. Every rail (`agent-bus`, `intercept`, `supervisor`, `deferred-confirm`'s `submitTo` flow) reads the same shape it reads today.
- **Author-side composition matches what `acceptedFrom`/`peers` already do.** Those fields already accept `@group`; the parser already expands them to concrete names. The new behaviour is symmetric for scalar routing fields — same surface syntax, same launch-time resolution, no new wire-level concept for authors to learn.
- **Two membership-declaration forms cover both name-bound and anonymous nodes.** The existing top-level `groups: { workers: [w1, w2] }` block stays for explicit-by-name membership; a new per-node `groups: [<name>]` field aggregates anonymous peers into the same group at launch. Both forms feed one resolved member list per group.

## Considered alternatives

- **Runtime group addressing (bus learns about groups).** `agent_send({to: "@reviewers"})` would have to either broadcast or pick a recipient at the wire level. Rejected: the bus is a one-socket-per-peer Unix-domain transport with no multicast or virtual-recipient primitive; introducing one would touch the wire format, every rail's `acceptedFrom` enforcement, and the supervisor inbox dispatch. The user's stated need is author-side anonymity, not runtime fan-out — there is no use case in scope that runtime groups solve which launch-time resolution doesn't.
- **First-listed pick for `supervisor: @group` and `submitTo: @group`.** Deterministic and easy to debug, but turns the group into a rename: a second member is dead weight unless workers explicitly target it by name. Rejected because it makes the syntax feel like a misnomer — "group" implies a pool of equivalent peers.
- **Auto-bidirectional `acceptedFrom` inference.** When a worker declares `submitTo: @reviewers`, the launcher would auto-add the worker's resolved name to each reviewer's `acceptedFrom`. Rejected: `acceptedFrom` is an authorisation rail; auto-adding entries based on what the *sender* claims to do inverts which side controls the accept-list. Hand-wiring the receiver's `acceptedFrom: ["@workers"]` (once, possibly via `group_bindings`) keeps the receiver authoritative and makes the validator's effective-acceptlist computation a local read.
- **Pooled top supervisors (relax uniqueness).** Allow multiple peers in the topology with `supervisor:` unset; round-robin escalations across them. Rejected for v1: opens hard distributed-systems questions (which top owns a given submission, what happens on top-1 crash mid-review, how the TUI mediates between concurrent escalate dialogs from different tops) that the user's framing did not request. Strict uniqueness keeps the escalation chain coherent. The relaxation is additive — a future ADR can introduce pooled tops without breaking single-top meshes.
- **Recipe-level `@group` references.** Allow recipes (`pi-sandbox/agents/<name>.yaml`) to declare `supervisor: @reviewers` and resolve at runtime against whatever topology is hosting them. Rejected: groups are a topology-level construct; embedding `@group` in recipes blurs that boundary, breaks `npm run agent` standalone runs (no topology, no group definitions), and creates failure modes that surface only at mesh launch. Topology overrides already cover the use case via `group_bindings`. Future seed-agent dynamic spawning will pass group references at runtime, not via recipe YAML.
- **`@group` in `entry:` round-robins like `supervisor:`.** Rejected: `entry:` is the TUI's initial focus; round-robin would mean launching the same mesh twice gives different focused peers. First-listed is deterministic across launches and matches operator expectations.

## Consequences

- **Topology schema** (`pi-sandbox/.pi/extensions/_lib/topology.mjs`) gains a per-node `groups: [<name>, ...]` field. Membership for a given group is the union of (i) names listed in the top-level `groups: { <name>: [...] }` block and (ii) nodes that declare the group in their per-node `groups:` field. Both forms remain supported; one source of truth is the *resolved* member list, computed at launch.
- **`@group` is accepted in scalar routing fields** (`supervisor:`, `submitTo:`) in addition to the existing array fields (`acceptedFrom:`, `peers:`) and the new `entry:` use. Resolution policy:
  - `supervisor:` and `submitTo:` — round-robin per worker over the resolved member list, in node-declaration order. The launcher logs each assignment to stderr (`worker w1 → supervisor reviewer-2 (round-robin)`).
  - `entry:` — first-listed member of the resolved list. Deterministic across launches given a stable member order.
  - `acceptedFrom:`, `peers:` — full expansion to all members (existing behaviour).
- **Empty `@group` resolution is a validation error**, regardless of which field referenced it. The validator catches it before any peer spawns.
- **Top-supervisor uniqueness rule (`topology-validator.mjs:130-168`) gains one wrinkle**: when computing each node's effective supervisor, `supervisor: @group` counts as "set" provided the group resolves to ≥1 member. The uniqueness rule is otherwise unchanged — exactly one node may be missing `supervisor:`, including when that node is itself a group member.
- **`entry:` becomes optional and defaults to the unique top supervisor.** Authors only write `entry:` to override the default (e.g. focusing a worker first for debugging). Explicit `entry: <name>` and `entry: @group` are both accepted; omitted `entry:` is no longer a validation error.
- **Recipes no longer accept `supervisor`/`submitTo`/`acceptedFrom`/`peers`; the runner rejects them at parse time.** Deletion shipped via #112. The `@group`-rejection guardrail noted above is therefore moot — a deleted field cannot be misused.
- **Habitat schema is unchanged.** `Habitat.supervisor` and `Habitat.submitTo` stay scalar strings; `Habitat.acceptedFrom` and `Habitat.peers` stay string arrays. The topology resolver writes only concrete names into the `--topology-overlay` JSON.
- **The example mesh `pi-sandbox/meshes/grouped-mesh.yaml` remains valid** under both the legacy top-level `groups:` block and the new per-node `groups:` field; new examples should prefer the per-node form when they include anonymous peers.
- **Pooled top supervisors and runtime group addressing remain explicitly out of scope.** A future ADR may revisit either; this ADR's mechanisms are forward-compatible with both (the launch-time resolver is the single point that would change).
